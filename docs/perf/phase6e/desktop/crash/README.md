# The Phase 6c worker-thread crash, found again (Mac, 2026-11-05)

Apple M5, Metal, Godot 4.7.2 official editor binary (`ed1daf0bf`, no symbols), 960×540 window. Each variant: 20 quick launches of `quick_low.json` (the default map streamed, low profile, the spawn, 0.2 s windows) with `godot --path . --windowed --resolution 960x540 -- --perf-config=quick_low.json`; a launch counts as crashed when Godot printed `Program crashed` or exited by a signal. The variants are temporary patches of `game/world/map_streamer.gd` at `1521209` (in this folder), never committed.

| Variant | What the start does | Crashed |
|---|---|---|
| v0 (`v0_threaded_prime.patch`) | today's setup (the streamed materials and the warm cells loaded on the main thread), then the prime's cells requested on threads from `Main._ready()`, all at once, collected with `load_threaded_get()` | 0 of 20 |
| v1 (`v1_threaded_prime_first_materials_on_threads.patch`) | as v0, but the materials and warm cells not loaded first, as in Phase 6c's first loader: the cells' loading threads create the materials | 3 of 20, then 2 of 20 (5 of 40) |
| v2 (`v2_main_thread_sleeps.patch`) | as v1, but the main thread sleeps 1.5 s after the requests and collects the finished loads (no waiting in `load_threaded_get()` while they run) | 0 of 20, 0 of 20 |
| v3 (`v3_one_request_at_a_time.patch`) | as v1, but one request at a time (request, collect, next) | 0 of 20, 0 of 20 |
| Final code (Phase 6e) | the map read and instantiated on threads behind the loading screen (`docs/STREAMING.md`, "Loading a map") | 0 of 20 |

All five crashes (macOS crash reports of 2026-11-05) were in a `WorkerThread` with the same stack in the Godot binary as the eleven Phase 6c reports of 2026-11-03: offsets `0x432fb24` (or `0x432fb38` for the SIGSEGV), `0x417f03c`, `0x3b015b4`, `0x322a204`, `0x3229c30`, `0x4d7c248`, …, thread start `0x1a5a7f8`; four were SIGABRT from Godot's crash handler after a signal 11, one a plain SIGSEGV. `backtrace_run15.txt` is Godot's own printout of one of them. The official binary has no symbols for Godot's code (only ANGLE's), so the crashing function is not named.

What it takes: several loading threads creating the same materials for the first time, and the main thread waiting in `load_threaded_get()` meanwhile (v1). Either alone does not crash (v2, v3). Godot 4.7.2's source shows the window: `ResourceLoader::load_threaded_get()` on the main thread loops while the load runs, calling `_ensure_load_progress()` → `RenderingServer::sync()` every millisecond; with a RenderingDevice a loading thread creates materials and meshes directly (`can_create_resources_async()`), and `RenderForwardMobile::mesh_generate_pipelines()` reads each surface material's `MaterialData` without a lock, while `MaterialStorage::material_set_shader()`, queued by another loading thread's `BaseMaterial3D` and executed by the main thread's sync, deletes and replaces that data (`memdelete(material->data)`). A use after free of that kind fits the stack (a worker thread inside `ResourceLoader`'s load task) and the conditions; without symbols it is the likely cause, not a proven one.

The rules the loader follows from this: the main thread never waits in `load_threaded_get()` for a load in flight (it checks the status, which runs the same sync, and collects a load only when it is finished); one map load at a time; materials are prepared on the main thread only after the map is read and instantiated, while no loading thread makes meshes with them; the occluder scene, loaded beside the later steps, has no meshes or materials.
